# 缮本 设计说明

本文写「为什么这么设计、接下来做什么」。怎么安装和使用见根目录 `README.md`；书该排成什么样，以规范 `guide/` 为准。

最后更新：2026-11-01。

## 1. 定位与边界

上传一本已有的 EPUB，经过体检、修复、识别结构、你确认，下载一本更规范、更好读的 EPUB 3。

**典型输入**
- 网上流传的粗排书：空格缩进、`<br>` 分段、行内样式、没有目录；
- 被转换工具打平的书：`calibre5` 之类的匿名类名，语义丢失；
- EPUB 2 老书、结构不合规的书。

**不做**
- 格式转换（TXT、DOCX、PDF、AZW3）和 OCR；
- 所见即所得的逐字编辑（交给 Sigil 等编辑器）；
- 阅读器厂商的私有扩展。

**定位的来由**（2026-10-22 定）：
1. 目标是任意符合 EPUB 3 规范的阅读系统，不绑定具体阅读器；
2. 要网页界面；
3. 独立软件，不和本地书库耦合；
4. 引入大模型辅助；
5. 只做「已有 EPUB → 更好的 EPUB」。

## 2. 设计原则

1. **原件不动**：每次生成都是新版本，原件始终可下载。原计划逐步撤销，实际做成「每次生成留一个版本（最近 5 个）」，效果相同、实现简单。
2. **检测与修复分离**：规则引擎按 `guide/07` 实现，每条规则有编号、严重度和修复等级（`auto`、`suggest`、`llm`、`manual`）。只有 `auto` 级会自动改。
3. **DOM 优先**：结构用解析器改；正则只作用于文本节点。
4. **幂等**：对输出再跑一遍修复，应当没有任何改动（由测试保证）。
5. **识别与样式解耦**：先确定每段内容「是什么」（角色），再由主题决定「长什么样」。
6. **渐进增强**：基础样式在 CSS 支持弱的阅读器上也能读；新特性只作增强。
7. **正文一字不丢**：重建前后按块比对文字、核对图片数；有意删除的内容（书内目录页、广告页、注释区小标题、重复封面）全部列出。
8. **大模型是顾问，不是作者**：只给判断，不改写正文；结论经用户在确认板上采纳后才落地。
9. **规范是唯一来源**：主题样式表、规则说明都由 `guide/` 生成（`scripts/build_theme.py`、`scripts/build_rules_meta.py`），代码里不另写一份。

## 3. 处理流程

```
上传 → 解析 → 体检（EPUBCheck + 规则）
          ├─ 仅规范修复：确定性修复
          └─ 排版重建：确定性修复 → 语义分析 → 成组结构识别 → 按确认板的决定取舍
                       → 按章重建 → 主题样式（只附带用到的模板）→ 导航与 NCX → 再修复一次
          ↓
        校验（EPUBCheck、文字逐块比对、图片数核对）→ 新版本 → 下载
确认板 ←→ 大模型分析（只给判断，采纳后写进决定，重新生成时生效）
```

原设计在「重建」和「校验」之间还有一步「资源优化」（图片、字体），属于 M4，尚未实现。

## 4. 语义识别：为什么按「段落样式组」确认

- **为什么按组**：一本书几万段，但「长得不同」的段落通常只有几十种。按组确认，用户只需点几十次，而不是逐段检查。
- **怎么分组**（`semantic.cluster_key`）：原元素、原类名、字号级、是否粗体、对齐方式、段首缩进都相同的段落归为一组。
- **锚点**：文字总量最多的一组视为正文，其他组都相对它判断，比如更大更粗的是标题、缩进更深加楷体的是引文。
- **规则和人各管一层**：
  - 规则按 `guide/04` 各节的「识别信号」分三级：A 是原书已标明，B 是信号充分，A、B 都自动改写；C 是把握不够，只列成建议。
  - 用户在确认板上可以整组改角色、逐个改标题级别、取消某处结构、执行某条建议。
  - 决定按稳定的键存储（类别 + 文件 + 文字摘要），同一本原书反复重建都能对上。
- **原计划没做的**：`calibre5`、`calibre6` 这种只差细微样式的类先行合并；按计算后的完整样式（字体族、颜色、边距）分组；确认板上拆分、合并组。

## 5. 大模型辅助

适合交给大模型的，是启发式不可靠、但看片段就能判断的事：

| 任务 | 发给模型的内容 | 模型 | 状态 |
|---|---|---|---|
| 段落样式组的角色 | 每组若干样例（含前后文）+ 原样式摘要 + 正文对照 | 轻量 | 已实现 |
| 结构是否成立 | B 级结构、C 级建议的段落与前后文（诗歌、书信、列表、剧本、术语表、广告…） | 轻量 | 已实现 |
| 标题层级与辅文类型 | 全书标题列表 + 章首一两句 | 重型 | 已实现 |
| 图片描述（alt） | 缩到 1024 像素的插图 + 图注 + 图前文字 | 轻量 | 已实现 |
| 注释配对 | 注号附近句子 + 候选注文 | 重型 | 未做：注号与注文互相链接时已能确定性配对，样本里没遇到无链接的情况 |
| 断行段落合并 | 相邻两段的结尾与开头 | 轻量 | 未做（M5） |

**实现要点**
- **接口**：Claude 原生接口，用 Anthropic 官方 Python SDK，暂固定 1.x：2.x 默认发的 API 版本 2026-10-21，部分中转还只认 2023-06-01。
- **配置**：地址与令牌按「网页设置 > 环境变量 `EPUBTS_LLM_*` > SDK 标准环境变量」读取，都不进仓库。
- **模型分两档**：轻量 Haiku 5.5 做大批量判断，重型 Opus 5.5 做要通盘考虑的判断。
- **输出**：结构化输出（Pydantic 模型校验），结果只进确认板，用户采纳后写进决定，重新生成时生效。
- **省钱与隐私**：
  - 只发片段，不发整本；
  - 系统提示走提示缓存；
  - 结果按内容哈希缓存在 `data/llm-cache/`，同样的内容只问一次；
  - 确认板显示调用次数和按官方价估算的费用。
- **容错**：中转的内容审核拦下某一条时，只跳过那一条并计数，不算失败。官方接口上会开拒答兜底（服务端改派其他模型）。

## 7. 技术选型（已定）

| 层 | 选型 |
|---|---|
| 后端 | Python 3.13、FastAPI；后台任务用进程内线程池 |
| XHTML、CSS | lxml、cssselect、tinycss2 |
| 字体、图片 | fontTools、Pillow |
| 校验 | EPUBCheck 5.4.0（Java），打进镜像；容器须是 UTF-8 locale，否则中文文件名会静默失败 |
| 前端 | Vue 3 + Vite |
| 大模型 | Anthropic 官方 Python SDK（1.x） |
| 部署 | 单个 Docker 镜像（后端 + 前端静态文件 + JRE）；单用户，不做登录 |

## 9. 风险

- **误判**：标题层级、注释配对、诗歌和书信识别都可能出错。不确定的一律只列建议，经确认才落地；重建后按块比对文字，防止丢内容。
- **阅读器差异**：各家对新 CSS 的支持参差。默认主题只用稳妥特性；`guide/03` 中标【需实测】的特性，要在 Apple Books、Thorium、KOReader 等上实测后再默认启用。
- **字体版权**：只做提示，不内置商业字体。
- **大模型费用与隐私**：片段化、缓存、可关闭；走中转时内容可能被中转方审核或记录，敏感书籍建议关闭大模型或用官方接口。
- **中转兼容**：中转对 API 版本、请求头的支持滞后于官方（见 §5 的 SDK 版本限制）。
